> 日期：2026-09-14 ｜ 状态：**路线图已定的部分标 ✅，其余待评估**
> 本文回答两个问题：① 同类项目怎么做、能借鉴什么 ② Python 生态里有哪些现成能力可用。

---

## 0. 三条最重要的借鉴

### ① 面向 agent 的设计里，「JSON 规格 + 工具发现」是赢家

同类项目里最接近本项目的定位是 **SlickFast**，它的自我描述是：

> A tiny JSON spec in → a finished, retina-quality chart out. **Milliseconds, a handful of tokens**,
> nothing leaves your machine. … **not a plotting library an agent has to write code against.**

那句 "**a handful of tokens**" 是关键 —— 它点出了一个容易漏掉的维度：

| 维度 | JSON spec | Python 代码 |
|---|---|---|
| **token 成本** | 低（几十 token） | **高（循环、import、样板代码）** |
| 可靠性 | 高（可 schema 校验） | 中（写错一处就跑不起来） |
| 表达力 | **低（受限于预设 op）** | **高（循环 / 条件 / 数学）** |
| 可复现 | 强 | 强（靠 seed） |
| 非程序员可用 | ✅ | ❌ |
| 远程 / 沙箱安全 | ✅ | ❌ |

**结论：不是二选一，而是双通道。**

- **JSON 场景 = 快通道**：覆盖常见需求，**token 最省、最可靠**
- **Python API = 逃生通道**：JSON 表达不了时（循环参数化、数学几何、条件逻辑）降级写代码
- 两者**共享同一能力层**，不重复实现

> 判断依据：SlickFast 能把 JSON 做成主接口，是因为**图表是窄域**。
> pixsmith 做的是"纹理 / 底图"，是**宽域** —— 宽域下 JSON 的表达力天花板会更早撞到，
> 所以双通道不是折中，是宽域的正确解法。

### ② 参考物要做成「可调用的工具」，不只是文档

- **SlickFast** 的 MCP 工具集里有两个专门服务参考物的：
  `explore`（返回每种图的数据结构 + **最小可用 spec**）、`show examples`（渲染示例画廊）
- **QuiverAI** 有 `list previous creations`（**列出自己以前的产物并可取回**）

→ 启示：`examples/` 不该只是给人看的目录，应该能被 CLI 以 JSON 输出（`pixsmith spec --json`
已经带上每个图案的 `minimal` 场景），**让 agent 自己翻**。

### ③ 能力分类法对齐 Pillow 的命名

Pillow 是 30 年验证的事实标准，它的模块划分就是"元能力"的权威分类。
**照它的名字命名，用户和 AI 的既有知识可以直接迁移**：

| Pillow 模块 | 语义 | pixsmith 对应 |
|---|---|---|
| `ImageDraw` | 图元绘制 | ✅ `Canvas` 的图元 + `ops.py` 的 draw 动词 |
| `ImageFilter` | 滤镜（卷积核类） | ✅ `filters.blur` / `box_blur` |
| `ImageEnhance` | 调整（Brightness/Contrast/Color/Sharpness） | ✅ `filters.adjust` |
| `ImageChops` | **混合模式（二元算子）** | ✅ `blend.py`（14 种） |
| `ImageOps` | 整体操作（colorize/posterize/solarize…） | ✅ `filters.posterize/solarize/invert/grayscale` |

## 2. Python 生态：**直接用 / 借算法 / 别碰**

> 原则：**能用 100 行 NumPy 写出来的，就不引依赖**。
> 依赖换来的应该是"我写不出来的东西"，而不是"我不愿意写的东西"。

### 2.1 借「分类法与算子清单」—— 不依赖

**Pillow** 的价值主要不在代码，在**它已经帮我们把"元能力"列全了**：

| 类别 | 算子清单（可直接照抄的命名） |
|---|---|
| `ImageFilter` | `BoxBlur` `GaussianBlur` `UnsharpMask` `BLUR` `SHARPEN` `SMOOTH` `DETAIL` `EDGE_ENHANCE(_MORE)` `CONTOUR` `EMBOSS` `FIND_EDGES` `MedianFilter` `ModeFilter` `MinFilter` `MaxFilter` `RankFilter` `Kernel` |
| `ImageEnhance` | `Brightness` `Contrast` **`Color`（饱和度）** `Sharpness` —— 统一 `enhance(factor)` 语义（1.0 = 原图） |
| `ImageChops` | `blend` `composite` `multiply` `screen` `overlay` `soft_light` `hard_light` `darker` `lighter` `difference` `add` `subtract` `invert` `logical_and/or/xor` `constant` `offset` |
| `ImageOps` | color：`autocontrast` `equalize` `grayscale` `colorize` `invert` `posterize` `solarize`；size：`flip` `mirror` `pad` `expand` `crop` `scale` `fit` `contain` `deform` |
| `Image.effect_*` | `effect_noise` `effect_mandelbrot` `effect_spread` `linear_gradient` `radial_gradient` |

**⚠️ 但不硬依赖 Pillow**，两个硬理由：

1. Pillow 的绘制是**整数坐标 + 无超采样**，本项目的覆盖率抗锯齿更精细；
2. 它的滤波结果**随版本变化** → 破坏"同输入同字节"的可复现承诺。

→ 定位为**可选增强后端**：检测到就多暴露一批直通算子（emboss / contour / median / rank…），
并明确标注这些算子的结果**不保证跨版本一致**。

### 2.2 借「算法」—— 自己用 NumPy 实现

| 库 | 借什么 | 为什么不直接依赖 |
|---|---|---|
| **noise (pnoise2)** | Perlin/Simplex + `octaves/persistence/lacunarity` 参数语义 | C 扩展，安装有门槛 |
| **opensimplex** | OpenSimplex 算法（无专利、无轴向伪影） | 纯 Python 太慢（见下表） |
| **pyfastnoiselite** | FastNoise Lite 的噪声类型全集（Perlin/Simplex/**Cellular**/Value） | 同上 |
| **scipy.ndimage** | `gaussian_filter` `uniform_filter` `sobel` `median_filter` 的**语义与边界处理** | scipy 是重依赖 |
| **scikit-image** | 颜色空间转换（rgb↔hsv/lab）、形态学（dilate/erode → 描边/加粗） | 重依赖 |

**性能佐证**（NoiseTexture 项目的实测，纯 Python vs Cython）：

| 算法 | 纯 Python | Cython | 倍率 |
|---|---|---|---|
| Perlin 2D | 1.26 s | 0.017 s | **74×** |
| Voronoi 2D | 1.78 s | 0.114 s | 16× |

→ 噪声算法**必须向量化**。而 Perlin / Value / Cellular / fBm 在 NumPy 里都能干净地向量化
（梯度表查表 + 五次插值；Cellular 用 3×3 邻域搜索）—— **约 100 行、零新依赖、结果确定**。
✅ 已落地于 `src/pixsmith/noise.py`。

### 2.3 借「数据」—— vendor 进来

| 库 | 借什么 | 做法 |
|---|---|---|
| **palettable** / **matplotlib cmaps** | 成熟配色表（Viridis / Spectral / Tableau / 中国传统色…） | 抽成纯常量或 JSON，**零依赖** |
| **colour-science** | 颜色空间公式 | 只抄公式 |

### 2.4 未来可选后端（现在不引）

| 库 | 用途 | 代价 |
|---|---|---|
| **skia-python** | 工业级 2D：真高斯、全混合模式、阴影、shader（Chrome/Flutter 同源） | 大依赖；但要"专业级效果"它是最短路径 |
| **moderngl** + GLSL | GPU 加速 / 实时预览 | 显卡依赖，破坏"随处可跑" |
| **cairosvg / resvg / svglib** | SVG → PNG 的桥 | 仅在需要"矢量栅格化"时才需要 |

### 2.5 双后端（PNG / SVG）—— ✅ 已落地

`Canvas` 的图元天然可表达为 SVG path，所以"同一套 API、两个后端"不需要重写语义：

| | 位图（`canvas.py`） | 矢量（`svg.py`） |
|---|---|---|
| 强项 | **逐像素纹理、噪点、非线性滤镜** | **矢量图形、锐利缩放、可编辑** |
| 弱项 | 缩放会糊、不可编辑 | 逐像素域表达不了 |
| PPT 场景 | 底图 / 背景 | **PPT 自 2016 原生支持 SVG**，适合图标与图示 |
| 滤镜 | 全部生效 | 部分可映射（`feGaussianBlur` / `feBlend` / `feColorMatrix`） |

落地结果：**23 个图案中 23 个位图可用、15 个矢量可用**；其余 8 个是逐像素场，
由能力校验**提前拦下并给出替代方案**（不静默降级）。

### 附：`render --report`（给 agent 的"眼睛"）✅ 已落地

agent 看不见图，所以需要程序化的间接反馈。`render --report` 输出：

```json
{"size": [1920,1080], "opaque_ratio": 1.0, "content_bbox": [0,0,1919,1079],
 "touches_edge": true, "dominant_colors": ["#0A1730","#C8102E","#F2C14E"],
 "mean_luma": 0.21, "contrast": 0.44, "fully_transparent": false}
```

判据很直接：**全透明 → 一定画错了**；非透明占比过低 → 大概率画到画布外了；
主色不对 → 参数传错了。

## 4. 刻意不做

| 不做 | 为什么 |
|---|---|
| **文字渲染** | 要 freetype / 字体文件，摧毁"轻量 + 无素材依赖"的立身之本。文字交给排版工具（PPT / HTML / 矢量软件） |
| **矢量→栅格化**（自己实现） | 已有成熟工具链；要栅格化就交给 `resvg` / `cairosvg` |
| **3D / 光照 / PBR** | 成本极高、收益极低 |
| **图像编辑**（裁剪 / 合成已有照片） | 那是 Pillow / ImageMagick 的活。本项目是**生成器**，不是处理器 |
| **万能 op 集合** | 绘图 DSL 的经典死法。op 只加"能跨后端表达"的那部分 |
